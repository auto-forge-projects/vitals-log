# DL-04-001: Veri saklama — gömülü `node:sqlite` (tek dosya DB)

- Tarih: 2026-08-10
- Faz: 4 — Çözüm Analizi
- Mod: AUTOPILOT
- Karar: Kayıtlar, Node stdlib'inin `node:sqlite` modülüyle yönetilen tek dosyalık bir SQLite veritabanında (`readings` tablosu, `ts` üzerinde index) saklanır. Erişim `ReadingStore { list, create, update, remove }` arayüzü arkasındaki tek adaptör dosyasından geçer; SQL başka hiçbir modüle sızmaz. Dış npm bağımlılığı eklenmez.
- Değerlendirilen alternatifler: (B) `better-sqlite3` npm paketi — aynı motor, olgun API ama native derleme + Alpine/musl riski; (C) düz JSON dosya deposu — tüm kayıtlar bellekte, her mutasyonda tmp+rename ile tam dosya yazımı.
- Gerekçe: C, FR-6'nın (çok cihazlı erişim) getirdiği eşzamanlı oku-değiştir-yaz senaryosunda sessiz kayıp güncelleme üretir ve FR-3/FR-4 tekil mutasyonlarında tüm dosyayı yeniden yazar; atomiklik/kilit kodu eklenince "en basit" seçenek olmaktan çıkar. B, A ile aynı garantileri verir ama sıfır-bağımlılık hedefini ve tek-container imaj sadeliğini yalnız "deneysel uyarı yok" karşılığında bozar. A'da NFR-4 (kalıcılık) ve veri bütünlüğü depo düzeyinde (transaction, NOT NULL/CHECK) zorlanır, NFR-1 index'li tek SELECT ile fazlasıyla karşılanır, `:memory:` DB testleri izole eder.
- Riskler: `node:sqlite` Node 22'de deneysel (ExperimentalWarning) — Node ≥22.5 ön koşulu Dockerfile'da sabitlenerek ve Faz 11 entegrasyon testiyle izlenir. DB dosyasının kalıcı volume'da olmaması veri kaybı doğurur → Faz 5/12'de volume yolu açıkça tanımlanacak.
- Geri alınabilirlik: Yüksek (`ReadingStore` arayüzü tüm erişimi kapsar; aynı SQL ile `better-sqlite3` adaptörüne ~1 saatte geçilir, DB dosyası aynen kullanılır; JSON'a taşımak `SELECT *` dökümüdür)
- İnsan onayı: Otomatik (AUTOPILOT, kalite kapısı geçti)
- Varsayım mı?: Hayır
