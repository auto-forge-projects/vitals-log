# DL-04-002: İstemci teslim biçimi — sunucu içi inline HTML + vanilla JS, JSON API

- Tarih: 2026-08-10
- Faz: 4 — Çözüm Analizi
- Mod: AUTOPILOT
- Karar: Arayüz, sunucu kodunda tutulan tek bir mobil öncelikli HTML sayfası + vanilla JS olarak servis edilir; CRUD işlemleri `/api/readings` JSON uçlarına `fetch` ile gider. Frontend framework, bundler ve build adımı YOKTUR. Tüm route'lar tek bir HTTP giriş noktasından (middleware zinciri) geçer — NFR-3'ün Faz 7'de seçilecek erişim kapısı buraya tek noktadan takılabilsin diye.
- Değerlendirilen alternatifler: (E) Sunucu tarafı HTML form + POST/redirect, JS'siz; (F) React/Vite gibi framework + bundle çıktısının imaja kopyalanması.
- Gerekçe: FR-1 kabul kriteri, aritmetik ortalama ve MAP değerlerinin **kayıt anında** hesaplanıp gösterilmesini ister; E bunu ancak kaydettikten sonra yapabilir (kullanıcı hatalı değeri kaydetmeden göremez, KPI-1 "≤30 sn" akışı bozulur). F, tek formluk bir üründe build zincirini, CI'ı ve imajı kalıcı olarak değiştirir — en yüksek kilitlenme riski, en düşük geri alınabilirlik ve mobil ilk açılışta NFR-1 aleyhine bundle maliyeti. D, sıfır bağımlılıkla FR-1 + NFR-2'yi (360px responsive, tam CSS kontrolü) birlikte karşılar.
- Riskler: JS kapalı tarayıcıda arayüz çalışmaz (tek kullanıcılı kişisel araç için kabul edilen risk). Elde yazılan CSS'in 360px doğrulaması manuel kalır → Faz 6/11'de somut viewport kontrolü listelenecek. Faz 7 katı bir CSP seçerse inline `<script>` bloklanabilir → Faz 5'te script'in ayrı bir route'tan servis edilmesi seçeneği açık tutulur.
- Geri alınabilirlik: Yüksek (sayfa tek modül + tek route; JSON API bağımsız kaldığı için ileride ayrı bir istemci eklenmesi mevcut sunucuyu değiştirmez)
- İnsan onayı: Otomatik (AUTOPILOT, kalite kapısı geçti)
